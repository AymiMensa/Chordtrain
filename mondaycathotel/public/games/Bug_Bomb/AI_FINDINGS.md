| 擊殺率 | 25.5% |

## 核心機制發現（推翻既有的策略假設）

用**遊戲真正的 Monster 物件**跑蒙地卡洛（`tools/bb-mc2.mjs`，546 顆炸彈樣本）：

| 條件 | 命中/總數 | 命中率 |
|---|---|---|
| **火場蓋住怪物「當下」的格** | **46/46** | **100.0%** |
| 逃逸出口 ≤ 1（傳統炸彈超人「陷阱」邏輯） | 75/530 | 14.2% |
| 火場面積 ≥ 5 | 63/319 | 19.7% |
| （基準：所有炸彈） | — | 16.2% |

**兩個結論：**

1. **「把怪物困在死角」在這個遊戲裡無效**（14.2% < 基準 16.2%）。
   傳統 Bomberman 的陷阱策略不適用。

2. **真正的機制是「炸彈阻擋怪物」**。
   `Monster.js` 的碰撞判定把「有炸彈的格」視為不可通行，
   所以炸彈不只是武器，它同時是一道圍牆。
   蓋住怪物當下的格 → 怪物被擋住跑不掉 → 0.5 秒的火焰掃到 → 必定擊殺。

## 未成功路（誠實記錄）

### 1. 參數演化搜尋 —— 停滯，未超越 V1

16 worker 島模型 GA，7 維參數空間，`tools/bb-evolve.mjs`。

**第一個教訓：過擬合。** 用 `EVAL_N=10` 時演化報出「通關 20%」，
但用全新種子做留出驗證（`tools/bb-validate.mjs`）後只剩 **0.5%**。
通關率是 ~4% 的稀有事件，10 場樣本量根本量不出來 —— 演化其實在最佳化雜訊。

**第二個教訓：搜尋會收斂到退化解。**
適應度函數給了存活加分，而通關在 7 維權重裡近乎不可達，
於是演化找到「幾乎不攻擊」：每場只放 1.0 顆炸彈、129/150 場超時。
19 代、60 萬場之後分數完全停滯。

結論：**瓶頸不在權重，在架構。** 連續的權重搜尋對這個問題無效。

### 2. BotV2 重寫 —— 更快但更弱，未接進遊戲

`src/game/ai/BotV2.js`：單一決策出口（每幀只做一次判斷、只產生一個決定），
消滅舊版 14 個放彈點 / 12 個互相競爭的狀態。
**每場 7.6ms vs V1 的 100ms（快 13 倍）**，讓大規模搜尋成為可能。

但實測 **0% 通關**，低於 V1 的 4.4%。原因：
決策核心簡化後缺少 V1 那些「笨但有用」的專門行為，
且加上的模擬式逃生保證器拒絕了 90% 的攻擊方案
（實測 `escapeFail=26037 / covered=29814`）。

**`BotV2.js` 目前未被 `src/main.js` 引用，保留作為未來工作的基礎。**

## 對「100% 通關」的誠實評估

條件一（蓋住怪物 = 100% 命中）已證實。
條件二（每次都能安全放彈並逃脫）**未達成**，且兩者互相衝突：
能蓋住怪物的位置，通常正是怪物逼得你無處可退的位置。

要同時滿足需要更精細的時序控制（等怪物進攻、拉開距離、算準引信），
遠超目前架構的能力。**目前沒有證據支持 100% 是可達成的。**

## 第二輪：因果干預實驗（用來決定「值不值得修」）

第一輪修的是 bug。第二輪用**因果干預**回答一個不同的问题：
目前 56% 死於自己的火，值不值得投入去修逃生？

### 方法論：為什麼不能只看觀測資料

先量測（`bb-headroom.mjs`，200 場 / 830 顆炸彈）：

| 指標 | 數值 |
|---|---|
| Bot 自認為安全 | 97% |
| 獨立驗證真的逃得掉 | 9.0% |
| 「不可逃」的炸彈實際造成死亡 | 15.2% |
| 「可逃」的炸彈實際造成死亡 | **21.3%** |

看起來像「檢查器在說謊」，但**驗證器本身沒有鑑別力**——
它說「可逃」的炸彈死亡率反而更高，方向是反的。
所以觀測資料無法支持任何結論，必須做干預。

（過程中我自己的驗證器有 bug：水平移動迴圈裡的 `[0,1]` 項目
計算 `nx = x + 0`，等於在問「當前位置會不會卡住」，答案永遠是否，
於是它宣稱「已移動」但 y 從沒變。修正後才得到上表。
**量測工具自己也會出錯，必須先驗證量測工具。**）

### 干預結果（`bb-intervene.mjs`）

| 策略 | 通關 | 死於自己的火 | 炸彈/場 | 超時 |
|---|---|---|---|---|
| 基準 | **4.7%** | 104 | 4.19 | 6 |
| 只放能逃的 | 0.0% | 7 | 0.30 | 71 |
| 只放能殺且能逃的 | 0.0% | 7 | 0.20 | 73 |

**禁止不可逃的炸彈，幾乎完全消滅了自殺（104 → 7），但通關率歸零。**
這是乾淨的因果證據：多放炸彈帶來的擊殺收益，
遠大於偶爾被自己炸死的損失。**逃生檢查器不是瓶頸，修它會把贏的能力一起修掉。**

### 「能殺且能活」的交集有多大（`bb-coverage.mjs`）

| | |
|---|---|
| 有任何能殺怪的格子 | 34.8% 的時刻 |
| 有「能殺怪 **且** 能活」的格子 | **10.7%** 的時刻 |
| P(能活 \| 能殺怪) | 20.9% |

交集存在但很小，而且干預實驗證明：**即使精確瞄准這個交集也沒用**
（smart = 0.0%）。因為要同時滿足兩者的時刻太少，Bot 等不到。

### 真正的結構性限制：炸彈容量（`bb-capacity.mjs`）

`Player.js` 的 `maxBombs = 1` —— Bot **一次只能帶一顆炸彈**。

| | |
|---|---|
| 觀察到的放彈速率 | 0.149 顆/秒 |
| 理論上限（maxBombs=1，引信 2.98s） | 0.335 顆/秒 |
| 容量利用率 | **41%** |

所以 Bot **不是**容量瓶頸。真正的結構是：
手上一颗、每次只能放一颗、放完要等爆炸 —— 炸彈供應是離散的、昂貴的。
這解釋了為什麼「減少放彈」必然導致 0% 通關：
通關需要炸彈，而炸彈供應本來就稀缺。

### 道具這條槓桿（`bb-items.mjs`）

Bot 的 `tryGather()` **只挑最近的道具，完全不管好壞**。
實測它會主動吃下：`NO_BOMB`（5 秒不能放任何炸彈）、
`BLIND`（5 秒失明）、`POISON`（8 秒操作混亂）、`REVERSE`（5 秒反向操作）、
`SLOW`、`CURSE`、`MINI`、`SLIPPERY`。

對一整場只放 4 顆炸彈的 Bot 來說，NO_BOMB 是災難級的懲罰，而它自願去吃。

干預測試（250 場）：

| | 通關 | 死於自己的火 | 炸彈/場 |
|---|---|---|---|
| 基準 | 5.2% | 150 | 4.12 |
| 過濾減益道具 | 5.6% | 150 | 4.14 |

**+0.4 點，在抽樣誤差內 → 無效，不合併。**
（邏輯上說得通，實測上沒用。誠實記錄為「無效」而非「略有效應」。）

## 第三輪：六次干預，以及一個被我親手推翻的規律

前兩輪修 bug、量上界。第三輪連續做**六次因果干預**，
看有沒有任何方向能突破 5.2%。

### 六次結果：全部失敗，但看起來有規律

| 策略 | 通關 | 死於自己的火 | 炸彈/場 | 超時 |
|---|---|---|---|---|
| smart（能殺且能活） | 0.0% | 7 | 0.20 | 73 |
| veto（只能活） | 0.0% | 7 | 0.30 | 71 |
| cover-only（只能殺） | 0.8% | 27 | 0.73 | 166 |
| opportunist（主動找殺怪位） | 0.8% | 116 | 3.08 | 80 |
| **BASELINE** | **5.2%** | 150 | 4.12 | 26 |
| no-debuff（過濾減益） | 5.6% | 150 | 4.14 | 27 |

看起來通關率完全由炸彈數決定：
```
bombs=0.20 -> 0.0%     bombs=3.08 -> 0.8%
bombs=0.30 -> 0.0%     bombs=4.12 -> 5.2%
bombs=0.73 -> 0.8%     bombs=4.14 -> 5.6%
```

我據此推導出結論：**瓶頸是炸彈供應，唯一方向是讓供應變多。**

### 然後我直接測了這個結論 —— 它是錯的

| maxBombs | 通關 | 炸彈/場 |
|---|---|---|
| 1（基準） | **5.2%** | 4.12 |
| 2 | 4.0% | 4.01 |
| 3 | 3.6% | 4.01 |
| 5 | 3.6% | 4.01 |

**把炸彈容量從 1 拉到 5，實際放彈量幾乎沒變（4.12 -> 4.01）。**

這推翻了上面的規律，並且找出真正的解釋：

> 前六次實驗中「減少炸彈數」的策略之所以通關率低，
> 不是因為「炸彈數是因」，
> 而是因為它們**順帶也擾動了決策層**。
>
> 而決策層**主動拒絕使用多餘的炸彈容量** ——
> 即使白白給它 5 顆的額度，它仍然只放 4 顆。

**真正的瓶頸是決策層，不是炸彈容量，也不是放彈策略。**
這與本輪稍早的量測（`bb-stall.mjs`）完全一致：
握著炸彈閒置佔全部時間的 55.1%，
其中 42.5% 有怪物在可及範圍內，但只有 6.1% 站對了位置。

### 這是本輪最重要的產物

前六次實驗各自失敗，卻共同指向同一個地方：
**所有試圖「限制放彈」的干預都失敗，因為放彈從來不是問題；
真正沒被解決的問題是「有炸彈、有怪物、卻不做決定」。**

而且現在知道了：**就算解決了這個問題，炸彈容量也已經夠用**
（容量利用率 41%，給 5 顆也只用 4 顆）。
瓶頸與遊戲平衡無關，純粹是 AI 架構問題。

### 過程中的三次自我糾錯

1. **量測工具**：逃生驗證器的移動軸寫錯（`[0,1]` 變成原地不動）。
2. **harness**：四個新腳本漏了 `im.checkPlayerCollection(bot)`，
   導致「Bot 從不拾取道具」的假結論。
3. **掛點**：opportunist 第一次掛在 `trySnipeAttack`，
   250 場只觸發 6 次，卻據此說「無效」。
   改掛 `canSafelyPlaceBomb` -> 186 次 -> +0.4。
   改掛 `think()` 入口 -> 66,285 次 -> -4.4。
## 第五輪：天花板實驗 — 終於找到真正的瓶頸

前四輪都在猜錯的維度上打轉。第五輪建立 **oracle**（理想化 Bot），
逐項加能力，看通關率在哪裡飽和。這是唯一能回答「100% 是否可行」的實驗。

### 結果（bb-ceiling2.mjs，200 場，第一關 3 隻怪物）

| 條件 | 通關 | 炸彈/場 | 擊殺/場 |
|---|---|---|---|
| 基準 | 4.5% | 4.13 | 0.71 |
| **oracle（完美瞄準）** | **6.5%** | 4.63 | 0.94 |
| **oracle + 不死** | **68.0%** | 9.01 | 2.48 |
| oracle + 8 顆炸彈 | 6.0% | 4.66 | 0.94 |
| oracle + 兩者 | 65.5% | 9.29 | 2.42 |

```
完美瞄準 vs 基準    +2.0 點
不死     vs oracle +61.5 點   ← 這才是瓶頸
8 顆炸彈 vs oracle   +0.0 點
```

**完美瞄準只值 +2.0 點，不死卻值 +61.5 點。**

而且「8 顆炸彈」單獨給幾乎無效（6.0%）——
**多顆炸彈只有活著才用得上**。這也回頭解釋了第三輪 supply 實驗為什麼失敗。

### 為什麼不死有這麼大的效果（bb-why.mjs，150 場）

| 存活秒數 | 場次 | 擊殺/場 | 炸彈/場 |
|---|---|---|---|
| 0–9 | 2 | 3.00 | 1.50 |
| 10–19 | 3 | 3.00 | 4.00 |
| 20–29 | 16 | 3.00 | 5.63 |
| 30–39 | 20 | 3.00 | 7.55 |
| 40–49 | 24 | 3.00 | 9.08 |
| 50–59 | 10 | 3.00 | 9.30 |
| 60+ | 75 | 1.92 | 10.45 |

**只要活過約 20 秒，擊殺數就是 3.00（全部清空），100% 通關。**
（60+ 那欄偏低是因為遊戲結束後仍在計時。）

關鍵是**炸彈數隨存活時間線性成長**（1.5 → 4.0 → 5.6 → 7.6 → 9.1 → 9.3），
而完美瞄準讓每一顆都必定命中。兩者相乘就足以清場。

### 這解釋了前四輪所有的失敗

現在回頭看，八次干預失敗的原因完全一致：

| 我以為的瓶頸 | 實際情況 |
|---|---|
| 逃生檢查器太鬆 | 放行率 98.7%，它幾乎不攔人 |
| 炸彈容量太小 | 給 8 顆也沒用（6.0%） |
| 瞄準率只有 11.7% | 完美瞄準只 +2.0 點 |
| 決策優先序錯了 | 不是優先序問題，是存活時間問題 |

**真正的瓶頸是：Bot 平均只活 30 秒，而需要約 20 秒以上且每顆炸彈都命中。**
現況是 30 秒存活 × 11.7% 命中率；需要的是 ~20 秒存活 × 100% 命中率。

### 這是 100% 通關的充分條件

在 oracle 的策略下（完美瞄準 + 存活），通關率達 68%，
且只要活過 20 秒就必定清場。剩下 32% 是活不到 20 秒的場次。

所以「100% 通關」在現行規則下**理論上可行**，
條件是：讓 Bot 在每場都至少存活 20 秒，同時每顆炸彈都命中怪物。

這與前四輪的結論（改規則才有用）**不同** ——
規則不需要改，需要的是一個「能撐 20 秒且瞄準正確」的 AI。
而這正是前四輪沒做到的：它們都只改一個維度，沒有人同時改善存活與瞄準。

### 但要誠實說明

目前的基準 Bot 是 30.1 秒存活、5.2% 通關。
oracle 是「完美瞄準 + 不死」。兩者之間的差距，
主要是**不死**貢獻的（+61.5），而完美瞄準只 +2.0。

所以務實的下一步是**改善存活**，不是改善瞄準。
但第三輪已證明「減少放彈能提高存活」，而那會降低通關率。

## 目標函數的教訓

第一輪演化搜索收斂到「活著但不贏」，當時我以為是演化能力不足。
現在知道那是**目標函數設計錯誤**：適應度裡存活有加分，
所以「活得久」被當成進步。

但第五輪的結果顯示**方向是反的**：
存活時間確實重要（+61.5），但必須搭配「每顆炸彈都命中」才會轉成通關。
單純優化存活會得到一個躲在角落裡動不了的 Bot —— 正是 V2 的下場。

正確的目標函數應該是：

```
score = 通關數 x 1000 + 擊殺數 x 10     （完全不含存活時間項）
```

讓演化在「通關」這個唯一有意義的指標上做選擇，
存活與瞄準會自動被找到正確的平衡點。

**先量測「干預實際觸發了多少次」，再相信它的結果。**
一個只觸發 6 次的鉤子給出的「無效」，什麼都證明不了。

## 第八輪（2026-10-30）：政策層結果論 + 新求解器 MCTSolver

### 做了什麼

1. **把「決策大腦」提升為可量測、可替換的政策層。**
   `Bot.js` 現在依 `window.__BB_POLICY_OVERRIDE` 或 `StrategyRegistry.selectPolicy()`
   選擇掛載哪一個 `think()`。兩種政策都完整保留——**沒有任何一種被刪除或被覆寫**。

2. **新求解器 `src/game/ai/MCTSolver.js`**，三個真本事都可在 `bb-bench2.mjs` 驗證：
   - **OR｜聯合「放彈位置 × 逃生」搜尋**。在 BFS 展開的可達集合上評分
     `12·期望擊殺 + 1.5·被擋住的怪 + 0.4·破磚 − 1.2·步數`；先以便宜幾何條件預篩，

   - **GT｜接觸不變式 + 損傷後撤退 + Stackelberg 合作協調**。任何怪與 Bot 的

3. **修掉兩個真實 bug（均附逐幀證據）**：
   - **撤退震盪**（`bb-ctrace.mjs` seed `-1640426806`，幀 1694–1737）：1-step greedy

     加入方向 hysteresis 與 BFS best-response 後消除。

### 第九輪（2026-10-31）：HUNT↔WANDER 決策抖振 —— 超時的真正主因

**先做版控**：把整條 AI 血脈收進版控（commit `022baad`，13 個檔案、+3960 行），
並把 `simulate*.js` / `*.bak*` / `*.checkpoint` 這類實驗暫存檔加進 `.gitignore`（commit `a63880b`）。

**新的量測工具**：`bb-ctrace.mjs` 現在會在「每次掉血前 30 幀」印出上下文
（phase / hp / 座標 / 輸入 / 最近怪距離），不必再從結尾自己回溯。

#### 找到的真 bug

`bb-ctrace.mjs` seed `-1640418887` 的第 40 秒暴露出一個和接觸死亡完全不同的失敗：

```
2377 WANDER  1 1,4  1.87 4.47 U  ZOMBIE@9,9 d=9.15   mon=2  scf=12
2378 HUNT    1 1,5  1.87 4.58 D  ZOMBIE@9,9 d=9.08   mon=2  scf=13
2379 WANDER  1 1,4  1.87 4.47 U  ...          scf=14
2380 HUNT    1 1,5  1.87 4.58 D  ...          scf=15
...（無限重複到 2400 幀上限，兩隻怪一隻都沒殺掉）
```

py 在 4.47↔4.58 之間來回、格子從未前進、`sameCellFrames` 無限成長。
**根因是兩套互相矛盾的目標函數每幀互相抵消：**

* `HUNT` 判定該往目標走（D）；
* 但下一步被 `monsterAdj` 或自身火場擋下 → `HUNT_HOLD`；
* 落到 `WANDER` 時，舊碼的唯一目標是「離怪最遠」→ 選了反方向的 U；
* 下一幀 `HUNT` 又要求 D → 永遠回不到目標。

這就是「決策抖振」：單看每一幀的決定都合理，合起來卻形成極限環。
它正好解釋了為什麼雙人合作 11/12 是超時、單人 5/12 是超時——
**不是不會殺，是根本走不到殺的位置。**

#### 修法

`WANDER` 是 `HUNT` 的「安全後備」，不是它的反向。評分改為：

```
安全 > 往目標變近 > 離怪遠 > 保留上一幀方向（hysteresis）
```

即使本幀不能照 HUNT 的路線走，也仍然在朝目標前進，兩套目標不再互相抵消。

### 第九輪之三：確認為什麼「走得動卻達不到目標」——HUNT 的路徑被自己的火擋住

`bb-diag2` 的 `huntNull`（20270 幀）＋ `huntHold`（25930 幀）排在拒絕原因的第二名。
HUNT 的 BFS 走訪函數是 `walkable && !hasBombAt && !unsafe`，而 `unsafe` 包含
**所有活彈的火場**。所以當 Bot 自己放的炸彈還沒爆，火場會把「通往怪的路」整段封住，
Bot 就只能在火場外繞，等 3 秒引信走完才繼續 —— 每顆彈浪費 3 秒的可走路徑。

這給出下一輪一個具體、可量測的改法：**HUNT 允許走進「引信快到的火場」**
（只要抵達時間早於該格引爆時間即可），而不是把整段火場都當牆。這與

### 第二十一輪（2026-10-31）：原因找到了 —— 是 eager 的 `getEscape()`，不是學習

用 `git checkout 076723f` 做乾淨基線比對，再逐步隔離，確認：

| 設定 | 第 1 關（N=48） |
|---|---|

| 學習碼 + `--no-learn`（舊版，eager 求值） | **87.5%（42/48）** ← 假的 |
| 學習碼 + `--no-learn`（修正後，短路面） | **72.9%（35/48）** ← 一致 |

#### 真正的原因

`findBestBombPlan` 的評分行把 `getEscape(cand.x, cand.y)` 當成
`learnedBonus(...)` 的**參數**傳入，所以即使 `blend=0`、函式主體直接 return 0，
**那個 `getEscape` 呼叫也已經發生了**。

`getEscape` 內部會呼叫 `bot.canSafelyPlaceBomb()` —— 這個遊戲最重的 BFS。
每幀對每個候選多呼叫數次，除了拖慢，更重要的是它與其他邏輯共用 `bot` 狀態，
足以讓整局的決策序列偏移，於是成績從 72.9% 變成 87.5%。

加上 `net.blend() <= 0 ? 0 : ...` 短路後，`--no-learn` 與真基線**完全相同**，
A/B 恢復可信。

#### 修正

```js
// 舊（錯）：eager 求值，副作用與學習無關
score = ... + LEARN_SCALE * learnedBonus(x, y, blastOf(...), getEscape(...));
// 新（對）：先判斷再求值
score = ... + (net.blend() <= 0 ? 0 : LEARN_SCALE * learnedBonus(x, y, blastOf(...), getEscape(...)));
```

### 第二十三輪（2026-10-31）：修好 bb-ownfire 的自洽性 —— 但要到正確歸因才敢簽名

上一輪留下一個未解問題：`games = dead + timeout + clear` 加不起來。
本輪定位並修好。

#### 根因（第五個量測工具的 bug）

舊碼在「任何 HP 下降」就 `rec[cause]++`，但 `games` 每場只記一次。
而 **hp=3 的角色可以掉兩次血還活著**，所以：

* 一隻 bot 掉血 → 記進 ownFire（或 monTouch…）
* 同一場最後 **TIMEOUT 或 CLEAR** → 又記一次 timeout/cleared

於是 `死因總和 + 死因總和 > games`，數字永遠加不起來。

#### 修法

把「診斷」和「結算」分成兩步：

1. 每幀只把每隻 bot **第一次受傷**的原因存進 `firstCause[i]`（不動計數器）
2. **本關結束時**，只對 `isDead` 的 bot 把 `firstCause[i]` 記進計數器

這樣兩條恆等式都成立、而且意義清楚：

```
games = dead + timeout + clear          （旅程級結果，互斥）
deaths = ownFire+bossBlast+monTouch+bossTouch+other   （bot 級死亡）
```

注意 `deaths ≥ dead`：COOP 一隻先死、另一隻續行到超時，journey 記 TIMEOUT，
但那隻 bot 仍計一次 deaths。這是設計如此，不是 bug。

或**實作「預判堵截」殺怪**（把 61.5% 單關天花板往上推）。
但即便兩者都成功，**60 關全破 100% 仍因連乘而不可達**——那需要規則層改變
（例如保證怪物必然走向玩家，讓堵截永遠可行）。

### 2026-11-08：修正隔離怪物誤判與安全破磚規劃診斷

根因：隔離怪物偵測使用「三步內找不到地板路徑」當成「被磚牆隔離」，遠處但可沿
地板到達的怪物也會被誤判，啟動不必要的安全破磚搜尋。現在改為完整地板連通搜尋；
判斷只看永久地形、忽略會消失的炸彈，且有計畫時也以相同搜尋檢查目標是否已可到達。
這只修正是否需要挖磚的分類，不改炸彈威力、候選距離、怪物碰撞守衛或 `getEscape()`
安全閘門。另加入規劃失敗原因計數，以區分超出搜尋半徑、炸不到磚、路徑沒有改善、
沒有安全逃生及逃生路徑碰怪。

單人第 2 關 30 次留出診斷：安全破磚搜尋由 535 次降至 219 次；找到計畫由 21 次
增至 28 次，找不到計畫由 514 次降至 191 次，實際 PKDIG 由 18 次增至 20 次。
這確認大量原搜尋是由錯誤隔離判斷觸發。修正後剩餘候選拒絕仍主要來自沒有安全逃生、
超出六格搜尋範圍、炸不到能降低目標路徑成本的磚；不應以放寬逃生限制掩蓋這些真實
